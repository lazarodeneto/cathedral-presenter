# Security audit — 6 November 2026

## Executive summary

Reviewed the React/TypeScript interface, Node backend, Electron IPC/navigation, media quarantine and Drive credentials, ZIP/document imports, shared workspace, output relay, controller API, dependencies and build packaging. Four concrete weaknesses were fixed in this pass. No unresolved critical/high finding was demonstrated in the reviewed local-installation threat model. This is source review and bounded adversarial testing, not a guarantee that the app has no vulnerabilities.

Test discovery is restricted to `src/**/*.test.{ts,tsx}` so local agent worktrees are not counted as application tests. Final local evidence: 62 application test files / 408 tests pass; typecheck, production frontend/backend build and ESLint pass. Full `npm audit --json` reports zero known vulnerabilities after resolving the development minimatch advisory. An unsigned packaged macOS arm64 app started its own backend, loaded its renderer and opened SQLite with a clean temporary profile. GitHub validation also passed tests, target-native packaging and clean-profile startup on macOS arm64 and Windows x64 ([run](https://github.com/lazarodeneto/church-presenter/actions/runs/42294726910)). Physical Windows/four-output hardware and Google account authorization remain unverified.

## Fixed findings

### 1. High — upstream HTML could execute on the trusted local origin

Rule: REACT-XSS-002 / JS-XSS-001. Location: `server/letrasgospelProxy.ts`, response sender, lines 71–77. Previously the proxy forwarded the provider's `text/html` content type. Direct navigation to a malicious/compromised upstream page could run provider scripts on the local app origin and access presentation data or perform same-origin authenticated operations. No upstream compromise was observed; this finding concerns the unsafe trust boundary.

Fix: force `text/plain; charset=utf-8`, add `nosniff` and a sandbox CSP. Client parsing still receives the original text. HTTP integration tests prove markup is returned only as non-executable data and cross-site requests are rejected.

### 2. Medium — incomplete browser-enforced response protection

Rule: REACT-CSP-001. Locations: `server/securityHeaders.ts:3`, `server/securityHeaders.ts:11`, `server/runtime.ts:18`, `vite.config.ts`. The production build previously embedded CSP in a meta element; `frame-ancestors` is not enforced there. The packaged server did not deliver equivalent response headers.

Fix: a shared production response CSP and `X-Frame-Options: DENY`, with nosniff/referrer headers in runtime/preview and appropriate development headers. Script sources stay same-origin without unsafe-eval/unsafe-inline. Inline styles remain necessary for canvas positioning. HTTPS image/media/connect sources remain supported for explicitly entered content. This policy is defense in depth, not a substitute for URL validation and React escaping.

### 3. Medium — unbounded upstream buffering/queue/cache

Location: `server/letrasgospelProxy.ts:27`, `server/letrasgospelProxy.ts:50`, `server/letrasgospelProxy.ts:64`. The old five-megabyte check happened after `arrayBuffer()` allocated the entire response, and waiting requests/cache could grow without bounds. Repeated local requests or a misbehaving provider could exhaust resources and interrupt presentation preparation.

Fix: stop and cancel streaming above five million bytes, maximum two active and 24 queued requests, and a 30 MiB bounded cache with expiry. Restrict access to loopback, valid local Host and same-origin/non-cross-site requests. A test confirms the oversized upstream reader is canceled.

### 4. Moderate — development dependency denial-of-service advisory

Location: `package.json:60`, `package-lock.json`. Advisory GHSA-g3hv-75wg-m249 affected transitive minimatch 9/10 instances used by linting/packaging. These were not shipped runtime dependencies. Blind audit fixes suggested unrelated major tool downgrades.

Fix: a scoped override upgrades only affected minimatch versions to the compatible modern API (lockfile resolves 11.0.5); old unaffected 3/5 instances remain intact. Full tests, lint, production build and actual macOS packaging were rerun. Complete dependency audit is now zero. Continue re-auditing future updates.

## Verified trust boundaries

- Better Auth password hashing, HttpOnly session cookies, origin checks and database-backed rate limiting; role is server-controlled, first-installation administrator claim is transactional.
- Media writes require sign-in, a custom request header, valid local origin/Host and loopback access. Images/audio/video are checked against file signatures and quarantined until a clean antivirus verdict. Missing scanner fails closed. Existing EICAR verification remains documented.
- Drive client configuration requires administrator/connection owner authorization, stays AES-GCM encrypted on disk and is never returned to the interface. New tests cover encryption/restart and refusal for anonymous/ordinary operators. OAuth uses expiring session-bound state and PKCE. Real Google authorization has not been performed.
- ZIP restore rejects traversal, duplicates, oversized entries and checksum failures, scans files and gives new identifiers before database commit. Infected restore leaves existing files intact. PowerPoint import accepts only bounded XML text; DTD/entity declarations are refused.
- Electron renderers have Node integration disabled, context isolation/sandbox/web security enabled and IPC restricted to the main operator frame on the local origin. Popups and remote navigation stay denied. The Google setup helper opens one fixed local media URL in the system browser; it does not expose an arbitrary URL launcher.
- Workspace, output relay and paired controller endpoints reject LAN/DNS-rebinding/cross-site access. Paired controller keys are random, stored as hashes, limited to allowlisted commands, rate-limited, expiring and revocable.
- Secret/private/generated directories are excluded from source artifacts and HTTP access. No account password, Drive token or user media file is included in the commit.

## Explicit limits and release gates

The installation is local and shared: offline presentation editing and reading scanned output files do not require a separate account. It is not a multi-tenant access-isolated cloud service and must not be exposed to the LAN/Internet. Local OS users with file access remain inside its trust boundary. Auth rate limiting currently uses a conservative shared per-path bucket because a trusted forwarded client IP is not configured; protection was not bypassed.

ClamAV binaries/signatures are machine dependencies and are not bundled in the installer. New machines must provision them before importing media. Email verification/reset delivery, signed/notarized installers, secure update distribution, Windows hardware testing, four-screen rehearsal and actual Google authorization remain release gates. Hardware acknowledgement does not prove physical pixels/audio; the current OS reports only one monitor until Samsung is reconnected.
